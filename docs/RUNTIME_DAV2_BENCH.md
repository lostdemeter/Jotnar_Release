# DAV2 on the warm runtime: first measurement

Status: research, branch `research/dav2-runtime-bench`. Not a gate.
Question: can the persistent Jotnar runtime replace a custom runner binary for
the DAV2 depth model, and is it fast enough to matter?

Short answer: **the runtime is the right control plane and a credible
persistent reference, but it is not a live production depth backend at
518 px.** One T2 layer costs ~29 s warm; the full T2 depth is roughly
170–350 s/frame depending on whether the compiled path is threaded. That is
in the same range as single-threaded compiled T2, and ~10,000× slower than
the 75.4 fps fast-float profile.

## Method

Release build (`target/release/jotnar-repl`), warm interpreter (`assemble once,
run many`), one real DAV2 layer-0 listing and payload at 112×112 (65 tokens)
and 518×518 (1370 tokens). Times are the interpreter's `--stats` `run` lines;
assembly is separate. RSS is `/usr/bin/time -v` maximum resident set.

Payloads were generated by the companion depth-conversion application:

```sh
# T2 layer 0
JOTNAR_BIN=<release jotnar> python scripts/dav2_layer0_nonfpu.py \
  --format t2 --size 112 --out /tmp/opencode/runtime_t2_112
JOTNAR_BIN=<release jotnar> python scripts/dav2_layer0_nonfpu.py \
  --format t2 --size 518 --out /tmp/opencode/runtime_t2_518

# Frozen-T layer 0 (same script, default --format t)
```

Warm run:

```sh
for i in 1 2 3; do cat payload.json; echo; done |
  target/release/jotnar-repl layer0.asm --outputs OUT --stats
```

The payloads are one JSON line each; `jotnar-repl` reads NDJSON and reuses the
assembled program. Assembly was <0.2 ms in all cases.

## Results

| workload | warm run (median) | max RSS | payload |
|---|---:|---:|---:|
| T layer 0, 112 (65 tok) | **0.259 s** | 308 MiB | 20 MB |
| T2 layer 0, 112 (65 tok) | **0.928 s** | 397 MiB | 24 MB |
| T layer 0, 518 (1370 tok) | **7.37 s** | 711 MiB | 25 MB |
| T2 layer 0, 518 (1370 tok) | **29.0 s** | 983 MiB | 30 MB |

Per-run variance was small (<2% at 518). The 112 px T2 run is ~3.6× the
frozen-T run; the 518 px T2 run is ~3.9×.

## Extrapolation

- **T2 12-block backbone at 518:** ~12 × 29.0 s ≈ **348 s** single-thread.
  The compiled single-thread T2 backbone is 310.7 s; the 16-thread fast-int
  backbone is 29.0 s. The runtime is therefore close to single-thread compiled
  and ~12× slower than the threaded fast-int profile.
- **Full T2 depth at 518:** ~350 s backbone plus neck/head; the compiled
  16-thread full-depth gate is 166 s. The runtime is roughly 2× slower than
  the threaded compiled path and in the same range as single-thread compiled.
- **Frozen-T 12-block at 518:** ~88 s; the compiled Rust float full depth is
  ~65 s. The runtime is ~1.4× slower.
- **Fast-float at 518:** 75.4 fps (13 ms). The runtime T2 layer alone is
  ~29 s; the complete native path is ~10^4× slower than fast-float.

Transport is not the issue: framed TCP measured ~10 µs overhead per job, and
one T2 layer is 29 s. JSON must not carry the 20–30 MB payloads; use framed
stores/execs.

## What this proves

- The persistent runtime can assemble and execute a real DAV2 T2 layer with
  no codegen, no per-frame process spawn, and no runner binary.
- Its warm latency is competitive with single-threaded compiled T2 at layer
  scale; the abstraction is not a toy.
- Weights can be staged once (payload/store size is ~30 MB per T2 layer;
  individual tensors fit under the node's 64 MiB frame limit).
- The in-process `NodeHandle` / external `jotnar-node` boundary is the right
  host-facing shape; network transport overhead is negligible relative to
  inference.

## What it does not prove

- Full-backbone or full-depth runtime latency (extrapolated from one layer).
- Node blob-store/exec with the full T2 four-plane weight set (next check).
- Memory for the full 12-block store (one layer is already ~1 GB RSS; the
  full store will be larger).
- Live performance. The runtime is single-threaded and does not use
  `CONFIG threads`; there is no GPU path.
- That the runtime should replace fast-float or compiled fast-int for live
  production.

## Update: deterministic threading (`research/jotnar-job-server`)

The follow-up experiment added a per-job execution thread budget and
output-partitioned kernels (MATMUL rows, CONV2D/DECONV2D output elements,
SOFTMAX rows) without changing any accumulation order. Results at 518 px:

- T2 layer 0: **~29 s → 2.65–2.71 s at 16 threads** (~10.9x), identical `OUT`
  hash.
- T2 neck: **63.9 s serial → 5.2 s at 16 threads** (12.3x), identical
  `NA0..NA3` hash. The old T2 convolution allocated one term vector per output
  pixel (460 GiB allocated for 170 MiB of output); one reused scratch buffer
  per worker removed the churn.
- T2 head: **39.0 s serial → 3.15 s at 16 threads** (12.4x), identical `OUT`
  hash (3 convolutions + resize).
- Full 12-block backbone: **335.4 s serial → 27.7 s at 16 threads** (12.1x),
  hash-identical. That is at or slightly faster than the compiled 16-thread
  fast-int backbone (29.0 s).
- Stage-wise full T2 depth (backbone + neck + head, 518 px):
  **~438 s serial → ~36 s at 16 threads**, hash-identical at every stage.
- Two concurrent backbone jobs at 8 threads each complete in 52.9 s (slowest)
  with the same output hash.

This supersedes the "single-threaded and ignores `CONFIG threads`" statement
above. The thread budget is independent of `CONFIG threads`; see
`docs/RUNTIME_THREADING.md` for the determinism contract, harness
(`jotnar-det`), and full profile.

## Recommendation

1. **Use the runtime as the native execution/reference engine**, not a custom
   runner binary. In-process `NodeHandle` for the SBS host; external
   `jotnar-node` for the runtime showcase/remote boundary; same `Node::handle`.
2. **Keep profiles explicit:** runtime T2 = exact canary/reference; compiled
   fast-int = exact speed profile; fast-float = live production default,
   WAIVED. The host writes the fidelity card.
3. **Do not call the runtime the live depth backend at 518** until a full
   backbone/depth measurement and a parallelism/optimization story exist.
4. Next experiments:
   - full 12-block T2 through the warm runtime (or 2-block scaling first);
   - `jotnar-node` store/exec with real T2 weights and a frame;
   - in-process `NodeHandle` depth prototype for the SBS host;
   - only then decide whether runtime performance work is worth it.
